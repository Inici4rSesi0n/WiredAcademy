# ADR-007 — DNI agnóstico de país

**Fecha:** 2026-11-08  
**Estado:** Aceptada

---

## Contexto

El campo `dni` (documento de identidad) fue validado históricamente como `VARCHAR(8)`, asumiendo que todos los usuarios tendrían DNI peruano (8 dígitos numéricos). Esto generó el **bug histórico** `value too long for type character varying(8)` cuando se ingresaba un valor de 9+ caracteres (registrado el 2026-10-18, corregido en Fase 9).

Además, el proyecto contempla **portabilidad internacional**. Los documentos de identidad varían por país:

| País | Documento | Formato | Longitud |
|---|---|---|---|
| Perú | DNI | Numérico | 8 |
| Chile | RUN | Numérico + K opcional | 8-9 |
| Argentina | DNI | Numérico | 7-8 |
| Uruguay | CI | Numérico | 7-8 |
| Brasil | CPF | Numérico | 11 |
| España | DNI/NIE | Numérico + letra | 9 |
| México | CURP | Alfanumérico | 18 |
| USA | SSN | Numérico | 9 |

Fijar `\d{8}` introduciría un **sesgo geográfico** que rompería la portabilidad del proyecto y obligaría a un refactor masivo si se decidiera internacionalizar en el futuro.

---

## Decisión

Se establecen **3 capas de validación** complementarias:

### 1. Capa física (base de datos)

- `usuarios.dni` es `VARCHAR(20)`.
- Migración `V2__widen_dni_column.sql`: `ALTER COLUMN dni TYPE VARCHAR(20)`.
- El widening es puro (no trunca, no pierde datos, no rompe el índice `usuarios_dni_key`).

### 2. Capa de dominio (`Usuario`)

- Invariante: `[A-Za-z0-9]{1,20}` (expresión regular).
- **Motivo:** previene el bug de BD (21+ caracteres o caracteres especiales) sin imponer el formato de un país específico.
- **Compatibilidad:** los tests de dominio históricos usan DNIs cortos (`"111"`, `"222"`, `"456"`) que siguen siendo válidos con esta regex.
- **Implementación:** en el constructor de `Usuario.java`, reemplaza la validación `dni == null || dni.isBlank()` por `dni == null || !dni.matches("[A-Za-z0-9]{1,20}")`.

### 3. Capa de negocio (`CrearUsuarioCommand`)

- Invariante: `[A-Za-z0-9]{4,20}`.
- **Motivo:** fail-fast en el flujo UI. Previene DNIs basura (`"1"`, `"ab"`) sin imponer un formato concreto.
- **Implementación:** compact constructor del record con validaciones de formato (dni, código, nombre, apellido, edad, rol).

### 4. Capa de presentación (controllers)

- `BootstrapController.confirmar`: valida formato DNI antes de construir el command.
- `SeccionGestionUsuariosController.handleGuardar`: idem.
- **Motivo:** mensaje de error claro al usuario (`Dialogos.info`) antes de intentar persistir.

---

## Consecuencias

### Positivas

- **Cierra el bug histórico** de `DataIntegrityViolationException` con mensaje claro.
- **Modelo compatible** con documentos de identidad internacionales.
- **Fail-fast** en UI (el usuario ve el error antes de guardar).
- **27 archivos de test preexistentes no se ven afectados** (los DNIs cortos siguen válidos en el dominio).
- **Portabilidad futura** sin refactor: si se decide añadir `pais` a `Usuario`, la validación específica se delega a un futuro `ValidadorDNI`.

### Negativas

- **Doble validación** (dominio laxo `1-20` + command estricto `4-20`) requiere que el desarrollador entienda por qué son distintos. Mitigación: este ADR lo documenta explícitamente.
- **Migración `V2`** requiere que cada entorno (local, CI) ejecute `mvn test` (o arranque la app) una vez para aplicar el cambio. El `ddl-auto=validate` de Hibernate fallaría sin la migración aplicada.

### Neutras

- **La validación específica por país** (ej. RENIEC para Perú, RUN para Chile) se difiere a un futuro `ValidadorDNI` cuando exista un campo `pais` en `Usuario`. La decisión actual no bloquea ese escenario: lo prepara.

---

## Alternativas consideradas

### Alternativa A — `\d{8}` estricto en `Usuario`

**Rechazada.** Motivos:

- Rompe 27 archivos de test unitarios que usan DNIs cortos (`"111"`, `"222"`).
- Introduce sesgo peruano en el dominio (viola portabilidad).
- Requiere migración V2 igualmente (no evita el trabajo de BD).
- La validación `\d{8}` es una regla de negocio, no un invariante físico. El dominio no debe imponerla.

### Alternativa B — `\d{8}` estricto solo en `CrearUsuarioCommand`

**Rechazada.** Motivos:

- No cierra el bug físico: otros flujos pueden construir `Usuario` directamente (ej. `GestionDocentes.agregar(new Docente(...))`) con DNI de 21+ caracteres y romper la BD igualmente.
- La validación laxa en `Usuario` es defensa en profundidad.

### Alternativa C — `\d{1,8}` en `Usuario` (solo numérico, 1-8)

**Rechazada.** Motivos:

- Solo numérico: rompe con Chile (K), España (letra), México (CURP).
- Solo hasta 8: obliga a migrar `VARCHAR(8)` de nuevo si se decide internacionalizar.
- Mismo coste de migración que la opción elegida (V2) sin sus beneficios.

### Alternativa D — Añadir campo `pais` al modelo ahora

**Rechazada (diferida).** Motivos:

- Scope creep masivo: cambiar modelo `Usuario`, entidades JPA, migración (añadir columna `pais`), UI (formulario), validadores por país, tests.
- No es requisito actual. El proyecto no tiene usuarios fuera de Perú todavía.
- La decisión actual no bloquea el escenario: cuando aparezca la necesidad real, se introduce `pais` y `ValidadorDNI` como evolución natural de este ADR.

---

## Reevaluar si

- Aparecen **casos de uso reales** con documentos que exceden 20 caracteres (pasaportes, cédulas complejas, identificadores tributarios largos).
- Se añade el campo **`pais`** a `Usuario` (se delegará validación a `ValidadorDNI` por país).
- Se integra el sistema con una **pasarela de validación de identidad** (RENIEC, SII, etc.) que requiera campos específicos.
- Se decide **migrar de `SINGLE_TABLE` a `JOINED`** (afectaría a índices y constraints de `dni`).
